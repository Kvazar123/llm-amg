# 12 — Установщик (`install.py`)

Документ описывает **внутреннее устройство установщика** `install.py`: как движок попадает в проект, как шаблоны рендерятся под среду, как блок активации вливается в точку входа и почему переустановка и удаление безопасны. Это взгляд «как сделано»; «как пользоваться» (порядок установки, флаги для пользователя, переустановка/удаление по шагам) — в корневом [INSTALL_RU.md](../../../INSTALL_RU.md). Дублирования между ними нет: здесь — механизмы и инварианты, там — рецепты.

> **Об именах путей.** `.claude` (каталог агента) и `CLAUDE.md` (точка входа) — умолчания Claude Code; установщик подставляет настроенные имена (например `.agents` / `AGENTS.md`). В шаблонах репозитория эти имена записаны как `.claude`/`CLAUDE.md` и служат **плейсхолдерами**, которые установщик заменяет.

## Что делает установщик

`install.py` — детерминированный, управляемый параметрами скрипт: модель ведёт диалог по [INSTALL_RU.md](../../../INSTALL_RU.md) и вызывает его с ответами, а файловую работу делает скрипт. По шагам он размещает движок, рендерит шаблоны точки входа и **сами промпты движка** под выбранный каталог агента, вливает блок активации между маркерами, сливает носитель хуков среды, рендерит команду `/amg` и (где профиль её объявляет) событийный плагин, при глобальной установке пишет **глобальный конфиг личных умолчаний**, пишет локальный `config.yml`, рендерит блок `models` в определения субагентов, засевает пустой `digest.md`, по желанию ставит зависимости и проверяет хранилище. Граф он **не строит** — активация остаётся выбором пользователя, а структурную сборку ведёт петля или `/amg sync` (флаг `--build` — явное исключение).

Запускается установщик **из каталога-чекаута AMG**, который может лежать где угодно — предпочтительно вне устанавливаемого проекта: движок копируется в каталог агента (`REPO = Path(__file__).parent` — источники берутся от расположения самого скрипта), и после установки чекаут не нужен. Чекаут внутри проекта не опасен — разрешение store отличает его от установленного хранилища по сигнатуре движка (см. «Как движок находит граф») — но и не нужен: он лишь захламляет проект.

## Две плоскости: движок и граф

Установка различает **движок** (переносимый код: скиллы, субагенты, конфигурация-шаблон) и **граф** (память конкретного проекта). Ключевой инвариант: **граф всегда локальный** — он лежит в `<проект>/<agent_dir>/amg/`, потому что память относится к проекту и между проектами не делится. Движок же можно поставить локально (в проект) или глобально (один на все проекты).

```mermaid
flowchart TD
    subgraph L["local (--scope local)"]
        LE["движок → <проект>/<agent_dir>/{skills,agents}"]
        LG["граф → <проект>/<agent_dir>/amg/"]
    end
    subgraph G["global (--scope global)"]
        GE["движок → ~/<agent_dir>/{skills,agents}<br/>(абсолютные пути в блоке)"]
        GG["граф → <проект>/<agent_dir>/amg/<br/>(всё равно локальный)"]
    end
```

В коде это разводят три пути в `install()`: `engine_root` (`Path.home()` при `global`/`project_only`, иначе `target`), `engine_agent_dir = engine_root/agent_dir` (куда лёг движок) и `graph_agent_dir = target/agent_dir` (корень графа — всегда от `target`). Точка входа — `engine_root/entrypoint`.

## Среды установки: пять режимов `--env`

Переносимость шире замены имени папки: формат скиллов SKILL.md — межинструментный стандарт (Agent Skills), а вот хуки, слэш-команды, `@`-импорт и формат субагентов у сред различаются. Поэтому установщик не только подставляет пути, но и **разворачивает механизм под среду** (классификатор `_env_kind`):

| `--env` | Среда | Что разворачивается |
|---|---|---|
| `claude-code` (умолчание) | Claude Code | блок со скиллами + хуки `settings.json` + слэш-команда `/amg`; модели → frontmatter `agents/amg-*.md` |
| `codex` | OpenAI Codex (есть скиллы, субагенты и хуковый движок ядра) | скиллы в `.agents/skills`, субагенты — **TOML в `.codex/agents`** (`model`/`model_reasoning_effort`), skill-aware блок `entrypoint/AGENTS.codex.md`, хуки сливаются в **`.codex/hooks.json`** (`SessionStart` → `start-check --hook-json`, `UserPromptSubmit` → `prompt-hint --hook-json`; обработчики с ключом `timeout_sec`, stdout обязан быть hook-JSON). Хуки работают **лишь после доверия через `/hooks`** — этим шагом завершается поток установки. Поверхности своих команд в актуальном Codex нет (обнаружимый вход — попап скиллов), события `SessionEnd` тоже нет |
| `opencode` | OpenCode (есть скиллы; `.agents/skills` находит сам) | скиллы в `.agents/skills`, субагенты рендерятся в **`.opencode/agent/*.md`** (`mode: subagent`; настоящий id модели проходит, Claude-алиас опускается), переносимый skill-aware блок `entrypoint/AGENTS.skills.md`, команда `/amg` — в **`.opencode/command/amg.md`**, **событийный плагин** — в **`.opencode/plugin/amg.js`**: замена хуков средствами OpenCode (стартовая проверка при создании сессии, гейтованное напоминание на каждое сообщение пользователя, дроссельный инкрементальный дамп стенограммы + атрибуция использования на idle) |
| `qwen` | Qwen Code (есть скиллы, markdown-субагенты, команды **и хуки**) | скиллы в `.qwen/skills`, промпты `agents/amg-*.md` ложатся в `.qwen/agents` (родные субагенты Qwen) с очисткой Claude-специфичного фронтматтера (`tools`/`effort` убраны; алиас модели убран, настоящий id проходит), тот же блок `AGENTS.skills.md` — в `QWEN.md`, команда `/amg` — в **`.qwen/commands/amg.md`** (markdown, подстановка `{{args}}`; TOML-формат команд Qwen объявлен устаревающим), сессионные хуки сливаются в `.qwen/settings.json` (Qwen читает hooks-блок Claude-формы) |
| `generic` | неизвестная AGENTS.md-среда | переносимый блок без скиллов `entrypoint/AGENTS.md`; хуки и команда не пишутся; скиллы всё равно ложатся в `.agents/skills`, и блок велит предпочесть их, если среда их обнаружит |

Каталог агента и точку входа установщик подставляет по среде, если они не заданы явно: Claude Code → `.claude`/`CLAUDE.md`, Qwen Code → `.qwen`/`QWEN.md`, иначе → `.agents`/`AGENTS.md`. **Режимы кроме Claude Code пока не протестированы живьём** (проверка сред — идущий сейчас этап дорожной карты); полный цикл памяти в OpenCode воспроизведён живыми полевыми прогонами, свежедобавленным плагину и команде своя проверка ещё предстоит.

### Реестр сред (`EnvProfile` / `ENVS`)

Всё, чем режимы установки *различаются*, — **данные, а не ветвления**: по одной замороженной записи `EnvProfile` на среду в словаре `ENVS` — пресеты `agent_dir`/`entrypoint`, имя шаблона блока, где живёт носитель хуков (`hooks_template`/`hooks_dest`), файл родной команды и её плейсхолдер аргументов (`command_dest`/`command_args`/`command_full`), назначение событийного плагина (`plugin_dest`), форма развёртывания субагентов (`subagents`: рендеренные markdown-копии, копии с очисткой под Qwen, TOML Codex или копии плюс родные рендеры OpenCode — с `native_agents`, называющим каталог и глоб родного рендера), поставляется ли форк-агент консультации (`ships_fork`), **пользовательская точка входа глобальной установки** (`global_entry`: `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.config/opencode/AGENTS.md`, `~/.qwen/QWEN.md` — ни одна из известных сред надёжно не поднимается выше корня проекта в домашний каталог, так что блок в `~/<точка входа>` остался бы непрочитанным; неизвестная среда сохраняет эту домашнюю догадку), и строка-заметка отчёта. `install()`, `uninstall()` и пресеты CLI — универсальные исполнители над профилем: блок вливается из `profile.block`, хуки сливаются в `profile.hooks_dest`, `render_command`/`render_plugin` возвращают `None` для профиля без такой поверхности, а удаление подметает назначения **всех** профилей (снятие установки не должно зависеть от памяти о том, какой `--env` её создавал). Поддержка новой среды — одна запись в реестре, плюс новая функция-форматтер лишь тогда, когда среда приносит действительно новый формат субагентов.

## Конвейер установки

```mermaid
flowchart LR
    PE["place_engine<br/>скиллы + промпты"] --> BL["блок активации<br/>inject_block"]
    BL --> HC["хуки · /amg · плагин<br/>(по профилю среды)"]
    HC --> GC["глобальный конфиг<br/>(только global)"]
    GC --> CF["config.yml<br/>write_config"]
    CF --> MD["модели → субагенты<br/>render_*"]
    MD --> DG["seed digest"] --> DE["deps"] --> VF["verify --repair"]
```

Ниже — каждый механизм по отдельности.

### Размещение движка и рендер промптов (`place_engine`)

Копируются **только** скиллы `amg-*` (`SKILL_NAMES`) и субагенты `amg-*`, поэтому в общем каталоге (особенно глобальном `~/.claude`) чужие скиллы и агенты целы, а переустановка обновляет лишь AMG. Скилл копируется целиком (`copytree`, без `__pycache__`); затем его `SKILL.md` и файлы `agents/amg-*.md` **рендерятся** функцией `render_control_text` под выбранный каталог агента. Дословное копирование оставило бы в иной среде неверные командные пути `.claude/...` и относительные пути скриптов, ломающиеся при глобальной установке. Reference-документы (`references/*.md`) остаются как есть — это документация; её средо-нейтрализация — этап перевода. Вместе со скиллами `place_engine` кладёт в `skills/amg-bootstrap/` и `VERSION` репозитория — установленный движок умеет назвать свою версию (`lifecycle.py version`, шапка status). Для `--env codex` файлы `agents/*.md` **не копируются**: субагенты Codex рендерятся отдельно как TOML (см. ниже).

### Рендер путей (`render_control_text`)

Единая функция замены плейсхолдеров в управляющем файле. Для **глобальной** установки пути к движку (`.claude/skills`, `.claude/agents`) становятся **абсолютными** (движок в домашнем каталоге), а пути графа (`.claude/amg`) и строка импорта дайджеста остаются проектно-локальными; `@`-импорт при global заменяется заметкой (глобальная точка входа не может импортировать пер-проектный граф). Затем `@.claude/amg`→`@<agent_dir>/amg`, `.claude`→`<agent_dir>`, `CLAUDE.md`→`<entrypoint>`. Для умолчаний Claude Code (`.claude`/`CLAUDE.md`, локально) результат совпадает с исходным шаблоном байт-в-байт.

### Блок активации (`inject_block`, `_block_body`)

Блок вливается в **конец** файла точки входа между маркерами `<!-- AMG:BEGIN -->` / `<!-- AMG:END -->`: инструкции пользователя остаются выше. `_block_body` срезает из шаблона стандартную преамбулу «# Project memory» (она нужна лишь для дев-копии), начиная с первого заголовка `## `. Переустановка заменяет **только** область между маркерами (идемпотентно: повторный запуск не дублирует блок); если файла нет — он создаётся с одним блоком.

### Хуки, команда и плагин (по профилю)

Носитель хуков называет профиль: `entrypoint/settings.json` сливается в `<agent_dir>/settings.json` для Claude Code и Qwen Code (Qwen читает hooks-блок той же формы), а `entrypoint/hooks.codex.json` — в `.codex/hooks.json` для Codex; сливатель один (`merge_settings`): чужие хуки и ключи сохраняются, прежние AMG-записи заменяются (по сигнатуре `lifecycle.py` в команде, независимо от события). Codex-шаблон отличается контрактом, а не формой: обработчики несут `timeout_sec` (не `timeout`), команды заканчиваются `--hook-json` (Codex внедряет только JSON-обёрнутый stdout), а `SessionStart` выполняет весь `start-check` — гарантированного модельного шага на старте у Codex нет (см. [08](./08-agents-skills.md)); запускает записи Codex лишь после доверия пользователя через `/hooks`. Команда `/amg` рендерится в родную поверхность профиля (`render_command`): дословно для Claude Code, усечённо — фронтматтер только с `description`, Claude-специфичный хвост срезан, плейсхолдер аргументов подставлен (`$ARGUMENTS` → `{{args}}` для Qwen) — для OpenCode и Qwen Code. Событийный плагин OpenCode рендерит `render_plugin` в `.opencode/plugin/amg.js` (при глобальной установке — в `~/.opencode/plugin/`, он на цепочке обнаружения OpenCode). Профиль без поверхности её просто пропускает — `generic` не пишет ни одной из трёх.

### Слои конфигурации: глобальный конфиг личных умолчаний (`write_global_config`)

При `--scope global` (и `--project-only` — он относится к уже существующей глобальной установке) установщик заводит **глобальный конфиг** `~/<agent_dir>/amg/config.yml` — слой личных, машинных умолчаний, который каждый установленный проект наследует по отдельным ключам. Его содержимое — блоки `models` и `retrieval.embeddings` со значениями из шаблона плюс ответы `--set-global` (точечные пути вида `retrieval.embeddings.enabled=auto`); заголовочный комментарий объясняет роль файла. Существующий глобальный конфиг **не перезаписывается** (то же правило, что у локального).

Чтобы наследование реально работало, локальный конфиг глобальной установки пишется **без** этих двух блоков — `_strip_top_block("models")` и `_strip_sub_block("retrieval", "embeddings")` вырезают ключ, его блок и баннерный комментарий над ним (полный шаблон затенял бы глобальный слой каждым своим ключом). Локальная установка (`--scope local`) самодостаточна: полный шаблон, глобальный файл не создаётся, `--set-global` игнорируется с пояснением.

Читают слои сами загрузчики движка (`retrieve` / `consolidate` / `extract_structure` — `load_config`): глобальный конфиг подкладывается **под** локальный слиянием по отдельным ключам (`_deep_merge`; вложенные блоки сливаются рекурсивно, локальное значение побеждает). Путь к глобальному слою выводится из ключа `agent_dir` **локального** конфига: он и называет домашний каталог среды (`~/<agent_dir>/amg/config.yml` — у каждой среды свой), и служит признаком «конфиг записан установщиком» — минимальный рукописный конфиг без `agent_dir` глобальный слой не читает, что держит тестовые фикстуры и ручные эксперименты герметичными. Каталог `~/<agent_dir>/amg/` при этом — носитель одного файла, **не хранилище**: графы в нём не создаются, а разрешение store его кандидатом не считает (см. «Как движок находит граф»). Установщик рендерит субагентов из того же объединённого взгляда (`_read_models` сливает глобальный слой под локальный), поэтому тиринг, заданный глобально, действует и без локального блока `models`.

### Шаблонизация `config.yml` (`write_config`)

`config.yml` копируется из шаблона репозитория, после чего заполняются отвеченные ключи. Правки точечные и **не трогают прозу комментариев**: `_set_scalar`/`_set_list` редактируют реальные строки-ключи (по якорю `^(# ?)?ключ:`), а не похожие фразы в комментариях. Заполняются `mirror_path`/`absorb_path`/`absorb_once_path` (флаг `--absorb-once`)/`exclude` (как flow-списки, элементы в кавычках — глобы остаются валидным YAML), скалярные ответы (`--set ключ=значение`; ключ с точками — например `retrieval.embeddings.enabled` — сеттер `_set_nested` находит по отступам внутри родительских блоков и меняет, сохраняя строчный комментарий), а также `agent_dir`/`entrypoint` (фиксируют выбор декларативно и включают наследование глобального слоя). Для не-`.claude` каталога единственное путь-значение `eval_gate.cases` тоже рендерится в выбранный каталог. **Целиком существующий `config.yml` никогда не переписывается** — переустановка бережёт конфиг и граф проекта, — но ключи, **явно переданные в запуске** (`--set` — скаляры и точечные пути, списки источников, `--exclude`), применяются к существующему файлу теми же точечными сеттерами и перечисляются строкой `updated keys:`: собранный установочным потоком ответ не имеет права молча пропасть (полевой сбой: поток спросил про засев, пользователь сказал «on», в конфиге осталось `auto`). `agent_dir`/`entrypoint` всегда следуют текущей установке. Всё не переданное остаётся как было и печатается строкой `in force:` для подтверждения.

### Тиринг моделей в субагентов (`render_agent_models` / `render_codex_agents`)

Блок `config.yml → models` — единственный источник правды по выбору моделей. Карта ролей → субагенты: `discovery`→{`amg-classifier`,`amg-retriever`}, `module_summary`→{`amg-builder`,`amg-linker`}, `synthesis`→{`amg-synth`,`amg-consolidator`}, `structural_extraction`→нет субагента. Значение роли — плоская строка-модель или `{model, reasoning_effort}`.

- **Claude Code, generic и guidance-копии OpenCode** (`render_agent_models`): пишет поля `model`/`effort` во frontmatter установленных `agents/amg-*.md` (точечной правкой, сохраняя `description`/`tools`/тело). Рендер выполняется для всех не-TOML-сред намеренно: даже там, где файлы — руководство петли, а не запускаемые субагенты, расхождение фронтматтера с конфигом дезориентирует (полевой сбой: в конфиге `opus`, в файле остался `sonnet`).
- **Qwen Code** (тот же `render_agent_models`, qwen-ветка): файлы в `.qwen/agents/*.md` — родные субагенты Qwen, поэтому Claude-специфичный фронтматтер вычищается: строка `tools` убирается (имена инструментов там чужие; отсутствие поля = все инструменты), `effort` убирается, а `model` пишется только настоящим идентификатором (проходит родной `qwen3-coder-plus` или чужой провайдер в qwen-форме с двоеточием `openai:gpt-4o`; Claude-алиас удаляется — Qwen берёт свою модель по умолчанию).
- **Codex** (`render_codex_agents`): рендерит `agents/amg-*.md` в TOML-субагентов `.codex/agents/amg-*.toml` — `name`, `description`, `developer_instructions` (тело промпта, пути отрендерены в `.agents`), и из конфига `model_reasoning_effort` плюс `model` (если это реальный id, а не Claude-алиас: дефолтные Claude-алиасы для Codex опускаются — Codex берёт модель сессии). Переустановка заменяет набор `amg-*.toml`, не дублируя.
- **OpenCode** (`render_opencode_agents`): рендерит `agents/amg-*.md` в `.opencode/agent/amg-*.md` — фронтматтер `description` + `mode: subagent` + `model` (только настоящие id; идентификаторы OpenCode имеют вид `провайдер/модель`), тело — промпт. Ограничение инструментов оставлено тексту промпта (ключи инструментов у OpenCode свои; частичная allow-карта молча меняла бы умолчания). Пишутся рядом с guidance-копиями в `.agents/agents/`; удаление вычищает и те и другие.

`reasoning_effort` **клампится по среде** (`_clamp_effort`): Claude Code `effort` = `low|medium|high|xhigh|max` (`minimal`→`low`), Codex `model_reasoning_effort` = `minimal|low|medium|high|xhigh` (`max`→`xhigh`); не задан — поле опускается. Полная семантика, кламп и апстрим-баг Claude Code [#44385](https://github.com/anthropics/claude-code/issues/44385) — в [Справочнике конфигурации](./09-config.md), «Модели субагентов».

### Засев дайджеста, зависимости, проверка

- **`seed_digest`** кладёт пустой `digest.md` (плейсхолдер), чтобы импорт/чтение дайджеста резолвились до первой консолидации; реальный дайджест не затирается.
- **`install_deps`** ставит запрошенные группы (`--deps`): `base` (`pyyaml` — единственная обязательная), `embeddings` (`model2vec`), `embeddings-st` (`sentence-transformers`), `text` (`pypdf`/`python-docx`/`openpyxl`), `treesitter` (`tree-sitter`/`tree-sitter-language-pack`); те же группы документированы в `requirements.txt`.
- **`verify_store`** инициализирует и проверяет **локальный** граф **установленным** движком (`graph_store.py init` + `verify --repair`) — **без сборки графа**. Флаг `--build` дополнительно строит структурный скелет (`reconcile.py bootstrap`); семантическое обогащение остаётся модель-ведомым.

### Пост-установочный шаг: перезапуск сессии

Управляющий слой, который установщик только что разложил, оживает лишь в **новой сессии**: агентная среда читает реестр скиллов и команд при старте сессии, поэтому установочная сессия не видит ни скиллов `amg-*`, ни команды `/amg`. Это важнее простого удобства: первая сборка, запущенная в установочной сессии, шла бы **без** скилла `amg-bootstrap` — модель импровизировала бы конвейер по тексту инструкции, теряя дисциплину оркестрации, которую скилл обеспечивает (ограниченные партии, контрольные части, пакетное применение). Поэтому модель-ведомый поток (INSTALL.md) завершается явной инструкцией о перезапуске, а первая сборка принадлежит свежей сессии — через петлю активации или `/amg sync`.

## Переустановка, удаление, добавление проекта

- **Переустановка** — это просто повторный запуск `install.py`, идемпотентный по построению: `place_engine` заменяет только `amg-*`, `inject_block` переписывает область между маркерами, `merge_settings` заменяет только AMG-хуки, `write_config` бережёт существующий конфиг (и печатает его действующие значения), рендер моделей переприменяется. Граф проекта не затрагивается. Модельный поток привязывает *режим* к тому же факту, что и скрипт, — к существованию проектного `config.yml`, — поэтому «переустановка» распознаётся по состоянию, а не по формулировке пользователя (INSTALL.md, шаг 0).
- **Удаление** (`--uninstall [--scope global] [--purge-graph]`) вырезает блок активации (содержимое пользователя цело) и подметает назначения **всех** профилей независимо от переданного `--env`: скиллы/агенты `amg-*`, родные рендеры субагентов (`.codex/agents/amg-*.toml`, `.opencode/agent/amg-*.md`), файлы команд и плагин OpenCode, AMG-записи хуков из каждого их носителя (`settings.json`, `.codex/hooks.json`) — чужие хуки целы. Граф **сохраняется**, пока не указан `--purge-graph`; глобальный конфиг личных умолчаний тоже (это данные предпочтений пользователя — установщик говорит об этом и оставляет удаление человеку).
- **`--project-only`** добавляет проект к уже существующей (обычно глобальной) установке: пишется только локальный `config.yml` + `digest.md` (и досоздаётся глобальный конфиг, если его ещё нет), движок/блок/хуки не трогаются.

## Как движок находит граф

Установщик фиксирует `agent_dir` в конфиге декларативно, но рабочий корень графа скрипты ищут **по расположению** (`graph_store.resolve_amg_root`): явный `--root` → `AMG_AGENT_DIR` → поиск вверх от текущего каталога (на каждом уровне сперва пресеты `<каталог>/{.claude,.agents}/amg/config.yml`, затем «голый» `<каталог>/amg` — только если это инициализированное хранилище) → расположение движка → умолчание `.claude`. Кандидат с сигнатурой движка (`skills/`, `agents/` или `install.py` внутри) отвергается как чекаут, уровень домашнего каталога пропускается (там живёт глобальный конфиг, не store). Поэтому глобальный движок лечит и читает **локальный** граф проекта, а чекаут AMG рядом с проектом ничего не перехватывает. Полные правила — [Хранилище и транзакции](./03-storage.md).

## Справочник флагов CLI

```
python install.py --target <проект> [--scope local|global]
    [--agent-dir .claude] [--entrypoint CLAUDE.md] [--env claude-code|codex|generic]
    [--mirror a,b] [--absorb c,d] [--absorb-once e,f] [--exclude "*.x,*.y"]
    [--set ключ=значение]...        # ключ с точками = вложенный (retrieval.embeddings.enabled)
    [--set-global ключ=значение]... # в глобальный конфиг личных умолчаний (global/project-only)
    [--deps base,embeddings,text,treesitter]
    [--no-verify] [--build] [--project-only]
python install.py --target <проект> --uninstall [--scope global] [--purge-graph]
```

Назначение каждого флага и сценарии — в [INSTALL_RU.md](../../../INSTALL_RU.md).
